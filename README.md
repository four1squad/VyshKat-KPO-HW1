1. Описание проекта

ВышКат - консольное приложение на C# для учета транспорта и имущества сервиса кикшеринга ВШЭ.

Программа позволяет:

добавлять электросамокаты, велосипеды и электровелосипеды
проверять исправность транспорта перед добавлением в парк
добавлять шлемы и зарядные станции
учитывать инвентарные номера и не допускать их повторения
считать количество транспорта и всех объектов на балансе
рассчитывать суммарнле суточное энергопотребление
выводить список транспорта, подходящего для новичков

Транспорт подходит для новичков, если простота управления составляет не менее 6 из 10 баллов.


2. Структура проекта

Проект разделен на два приложения:
VyshKat.App - основная программа
VyshKat.Tests - юнит тесты

Основные папки:

Models - классы транспорта и имущества
Interfaces - интерфейсы для инвентаря, энергопотребления и техосмотра
Services - логика учета парка и проведения техосмотра
ConsoleUI - вз-е с пользователем через консоль

Каждый класс и интерфейс находтся в отдельном файле.


3. Основные решения

Интерфейс IInventoryItem содержит название и инвентарный номер.

Интерфейс IEnergyConsumer реализуют только объекты, потребляющие электричество (зарядные станции тоже).

Для транспорта абстрактный класс Transport, от которого наследуются Scooter, Bicycle и ElectricBicycle.

Перед добавлением транспорта вызывается ServiceCenter. Техосмотр проверяет свойство IsWorking (если транспорт неисправен, он не добавляется).

После завершения работы список объектов не сохраняется.


4. Принципы SOLID

S
Каждый класс выполняет свою задачу (ServiceCenter проверяет исправность транспорта, FleetService отвечает за учет парка, ConsoleMenu отвечает за ввод и вывод).

O
Для добавления нового вида транспорта можно создать новый класс, наследующий Transport. При этом основные методы FleetService изменять не нужно

L
Классы Scooter, Bicycle и ElectricBicycle наследуются от Transport. Они могут передаваться в методы, которые работают с базовым классом, например в AddTransport().

I
Интерфейсы IInventoryItem и IEnergyConsumer раздлены. (Шлем не должен содержать свойства энергопотребления, поэтому реализует только IInventoryItem).

D
FleetService зависит от интерфейса IServiceCenter, а не от конкретного ServiceCenter

Принцип разделения интерфейсов позволяет учитывать разные объекты, не добавляя им ненужные св-ва.

Принцип открытости/закрытости реализован не полностью. При добавлении нового транспорта логика учета не меняется, но меню придется дополнить. Для небольшого консольного приложения, как это, это приемлемо, потому что создание отдельной системы регистрации видов транспорта сильно усложнило бы проект.


5. Возможное расширение

Если потребуется добавить новый транспорт (например электроскутер), можно создать новый класс наследник Transport. Для учета энергопотребления нужно реализовать IEnergyConsumer.

При добавлении сотрудников потребуется отдельная модель, тк сотрудники не являются имуществом на балансе

Для склада запчастей можно создать отдельный сервис, который будет управлчть остатками. Существующие классы транспорта и техосмотра не переписывать.


6. Dependency Injection

Для внедрения зависимостец исп-ся Microsoft.Extensions.DependencyInjection.

В Program.cs регистрируются IServiceCenter, FleetService и ConsoleMenu.

Контейнер создает объекты и передает зависимости через конструкторы.

В тестах используется FakeServiceCenter, который позволяет заранее задать результат техосмотра. Это помогает проверить поведение FleetService независмо от настоящей проверки исправности


7. Тестирование

Для юнит тестов используется xUnit

Написаны тесты, которые проверяют:

создание объектов с коррект и некоррект данными
успешный и неуспешный техосмотр
добавление транспорта после проверки
отказ при повторении инвентарного номера
расчет суммарного энергопотреб
выбор транспорта для новичков
поведение программы при пустом парке

Также приложение проверялось вручную через консоль
